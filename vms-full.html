01 — ปัญหา

มาพบ 1 ครั้ง ต้องผ่านหลายมือก่อนถึงตัว Host

กว่า Visitor จะได้พบ Host ต้องลงทะเบียน รออนุมัติ ยืนยัน Consent บางรายต้องอบรม แล้วจึงผ่านประตู พบเสร็จยังต้องแจ้งจบและสแกนออก แต่ละขั้นมีคนรับผิดชอบต่างกัน

ที่มา: สรุปจาก requirement ของโปรเจกต์
ฝั่งหน้างาน
  1. 01
    ข้อมูลผู้มาติดต่อกระจายหลายช่องทางข้อมูลส่งต่อผ่านโทรศัพท์ อีเมล และการแจ้งด้วยตนเอง เสี่ยงตกหล่น
  2. 02
    ไม่รู้ว่าอนุมัติแล้วหรือยังSecurity ไม่รู้ว่า Host อนุมัติแล้วหรือยัง ต้องโทรถามเอง
  3. 03
    มองไม่เห็นว่าใครอยู่ในพื้นที่ไม่รู้ทันทีว่าใครยังอยู่ เข้ามาทางไหน หรือพบเสร็จแล้วหรือยัง
ฝั่งองค์กร

ต้องเก็บ Consent ตาม PDPA ก่อนออก QR บางรายต้องผ่านการอบรมก่อนเข้าพื้นที่ และทุกการเข้า–ออกต้องดูย้อนหลังได้ว่าใครเป็นคนยืนยัน

ข้อจำกัดในการออกแบบ
Handheld จอเล็กSecurity ใช้ Handheld ที่ประตู หน้าจอต้องอ่านและตัดสินใจได้ง่าย
ใช้งานที่หน้างานVisitor, Host และ Security ใช้งานขณะยืนหรือเดิน ไม่ได้นั่งหน้าคอม
โจทย์การออกแบบ

ทำให้แต่ละบทบาททำงานต่อกันได้ โดยรู้ว่าผู้มาติดต่ออยู่ขั้นตอนไหน

02 — ผู้ใช้

ใครใช้ระบบ และต้องการอะไร

ผู้ใช้หลักคือ Visitor, Security, Host และ Admin ส่วน Trainer เข้ามาเฉพาะรายที่ต้องอบรม

  1. 1
    Visitor ต้องเข้ามาได้โดยไม่ต้องติดตั้งแอปส่วนใหญ่มาครั้งแรก และมาแค่วันเดียว
  2. 2
    Security ต้องรู้ทันทีว่าให้ผ่านได้ไหมยืนอยู่ที่ประตูทั้งวัน มีแค่ Handheld จอเล็กในมือ
  3. 3
    Host ต้องอนุมัติได้จากมือถือไม่ได้นั่งหน้าคอมตลอด แต่เป็นคนเดียวที่รู้ว่าแขกมาทำอะไร
  4. 4
    Admin ต้องเห็นภาพรวมและตรวจย้อนได้ดูแลข้อมูลผู้มาติดต่อ การตั้งค่า และรายงานบน Desktop

04 — การเปลี่ยนสถานะ

สถานะเปลี่ยนตามเหตุการณ์จริงหน้างาน

สถานะเปลี่ยนได้เมื่อคนที่มีสิทธิ์กดยืนยันเท่านั้น ตารางนี้แสดงทุกจุดที่สถานะเปลี่ยน ครบทั้ง 7 สถานะ

จากสถานะใครทำอะไรไปสถานะระบบทำต่อ
T1เริ่มต้น
HOST · VISITOR · SECURITYสร้างรายการผู้มาติดต่อ (นัดล่วงหน้า / ลิงก์ / Walk-in / Temporary Card ครั้งแรก)
→รออนุมัติแจ้ง Host ให้อนุมัติ
T2รออนุมัติ
HOSTอนุมัติ
→รอมาถึงส่งคำขอ Consent ให้ Visitor ยืนยันแล้วจึงออก QR
T3รออนุมัติ
HOSTปฏิเสธ + ระบุเหตุผล
→ปฏิเสธแจ้ง Visitor ทางอีเมล ถ้าเป็น Walk-in แจ้ง Security บน Handheld
T4รอมาถึง
SECURITYสแกนเข้าที่ประตู
→เข้าพื้นที่แล้วนับเป็นผู้มาติดต่อที่อยู่ในพื้นที่
เงื่อนไขก่อนสแกนเข้า · ระบบตรวจให้อัตโนมัติ
✓ Consent Edge 02ยืนยันแล้ว หรือยืนยันที่หน้างานก่อนเข้า
✓ การอบรม Edge 01ระบบเช็คว่าต้องอบรมไหม และแสดงวันที่อบรมล่าสุด ถ้าหมดอายุต้องอบรมใหม่ก่อน
✓ ช่วงเวลา QR Edge 03ใช้ได้ตั้งแต่ 15 นาทีก่อนนัดจนสิ้นวันนัด
T5เริ่มต้น
SECURITYสแกน Temporary Card (ครั้งถัดไป)
→เข้าพื้นที่แล้วไม่ต้องรออนุมัติ ระบบเช็คว่าบัตรยังไม่หมดอายุและเข้าพื้นที่นี้ได้
T6เข้าพื้นที่แล้ว
HOSTยืนยันว่าพบแล้ว
→พบ Host แล้วยังนับอยู่ในพื้นที่
T7พบ Host แล้ว
HOSTยืนยันจบการพบ
→จบการพบยังนับอยู่ในพื้นที่ จนกว่าจะสแกนออก
T8จบการพบ
SECURITYสแกนออกที่ประตู
→ออกแล้วนำออกจากจำนวน "อยู่ในพื้นที่ตอนนี้"
ใครเปลี่ยนสถานะอะไรได้Host ยืนยันการพบ · Security ยืนยันการเข้า–ออก
อยู่ในพื้นที่ตอนนี้นับตั้งแต่สแกนเข้าจนสแกนออก แม้จะจบการพบแล้ว
สถานะสุดท้ายออกแล้ว และ ปฏิเสธ เปลี่ยนต่อไม่ได้ ถ้าจะเข้าอีกต้องลงทะเบียนใหม่ ยกเว้น Temporary Card ที่ใช้บัตรเดิมได้จนหมดอายุ
05 — Solution ที่ออกแบบ

7 หน้าจอ เรียงตามเส้นทางของผู้มาติดต่อ

เริ่มจากลงทะเบียน อนุมัติ Consent และอบรม ไปจนถึงติดตามว่าใครยังอยู่ในพื้นที่ แต่ละหน้าจอระบุอุปกรณ์และบทบาทที่ใช้

S01 · Desktop + Mobile

ลงทะเบียน — จุดเริ่มต้นของข้อมูลผู้มาติดต่อ

  1. เริ่มได้ 2 ทาง: Host "สร้างผู้ติดต่อใหม่" หรือ "คัดลอกลิงก์ลงทะเบียน" ส่งให้ Visitor กรอกเอง
  2. ทั้ง 2 ทางได้ข้อมูลรูปแบบเดียวกัน
UX · ไม่ต้องกรอกแทนทุกราย

Host ส่งลิงก์ให้ Visitor กรอกข้อมูลเองได้

S02 · Mobile web · Host

Host อนุมัติ Security เห็นผลที่ประตู

  1. มีแค่ Host ที่อนุมัติหรือปฏิเสธได้
  2. Security เห็นผลอนุมัติ แต่แก้ไม่ได้
  3. ข้อมูลผู้มาติดต่อและเอกสารอยู่ในหน้าเดียว
UX · ตัดสินใจจบในหน้าเดียว

Host ตัดสินใจได้โดยไม่ต้องเปิดหน้าอื่น

เลื่อนดูทั้งหน้า ↕
สถานะ "รออนุมัติ"เห็นได้ทันทีที่หัวการ์ด
เอกสารประกอบHost เปิดดูเอกสารที่แนบมาได้ในหน้าเดียวกัน
ปฏิเสธ · อนุมัติปุ่มอยู่ล่างจอตลอด กดได้โดยไม่ต้องเลื่อนลงสุด

ทางที่ไม่เลือก · ให้ Security อนุมัติแทนที่ประตู เพราะ Security ไม่รู้ว่าแขกมาทำอะไร

S03 · Mobile web · Visitor

Consent → QR — ยืนยันเงื่อนไขก่อนรับ QR

  1. อีเมลแรกพาไปยืนยันเงื่อนไขก่อน ยังไม่มี QR
  2. Visitor ยินยอม PDPA และกฎการเข้าพื้นที่
  3. หลัง Consent ระบบส่ง QR ทางอีเมล
UX · รู้ว่าทำไมยังไม่มี QR

Visitor เห็นว่าต้องยืนยันเงื่อนไขก่อน จึงไม่ต้องโทรถามว่า QR อยู่ไหน

DECISION Consent ก่อนออก QR
ที่มา
องค์กรกำหนดให้เก็บ Consent ตาม PDPA ก่อนออก QR
ตัดสินใจ
ขอ Consent ทางอีเมลก่อนวันนัด ออก QR หลังยืนยันเท่านั้น ถ้ายังไม่ยืนยัน ทำที่หน้างานได้
เพราะ
เพิ่ม 1 ขั้นตอนก่อนวันนัด แต่มีทางสำรองที่หน้างาน
ไม่เลือก
ให้ทุกคนยืนยัน Consent ที่ประตู เพราะทำให้คิวหน้าประตูยาวในช่วงเช้า
DECISION QR บนมือถือ คู่กับ QR พิมพ์กระดาษ (QR Carbon)
ที่มา
ผู้มาติดต่อบางรายใช้ QR บนมือถือไม่ได้
ตัดสินใจ
พิมพ์ QR ลงกระดาษ สแกนได้เหมือน QR บนมือถือ
เพราะ
ทุกคนผ่านประตูแบบเดียวกัน แลกกับต้องพิมพ์ที่หน้างาน
ไม่เลือก
ให้ Security กรอกข้อมูลแทน เพราะคนกลุ่มนี้จะไม่ผ่านการตรวจ QR เหมือนคนอื่น
S04 · Mobile web · Trainer

Training — ยืนยันการอบรมก่อนเข้าพื้นที่

  1. ใช้เฉพาะผู้มาติดต่อที่ต้องอบรม หรือผลการอบรมหมดอายุ
  2. Trainer สแกน QR จากบัตรและตรวจสอบตัวตน
  3. Trainer ยืนยันผลการอบรม ระบบบันทึกผลไว้กับข้อมูลผู้มาติดต่อ
UX · ไม่เพิ่มขั้นตอนให้ทุกคน

อบรมเฉพาะคนที่ต้องอบรม คนอื่นไม่ต้องผ่านขั้นนี้

S06 · Desktop

Temporary Card — บัตรเดียวสำหรับการเข้า–ออกหลายครั้ง

ตอนออกบัตรกำหนดวันที่ใช้ได้และพื้นที่ที่เข้าได้ Host อนุมัติแค่ครั้งแรก ครั้งต่อไปสแกนบัตรเข้าได้เลย บัตรหมดอายุเองหรือปิดได้ทันที

UX · ไม่ต้องเริ่มใหม่ทุกครั้ง

ผู้ที่มาหลายครั้งไม่ต้องลงทะเบียนและรออนุมัติซ้ำ

S07 · Desktop + Handheld

ผู้มาติดต่อวันนี้ — เห็นสถานะเดียวกันทุกเครื่อง

  1. “อยู่ในพื้นที่ตอนนี้” เป็นตัวเลขหลักบนทั้ง Desktop และ Handheld
  2. Desktop แสดงสถานะทั้งหมด เพื่อให้เห็นภาพรวมของผู้มาติดต่อวันนี้
  3. Handheld แสดงเฉพาะสถานะที่ Security ต้องใช้ที่ประตู
  4. เปลี่ยนสถานะที่เครื่องไหน อีกเครื่องก็เห็นสถานะเดียวกัน
UX · ดูตัวเลขเดียวก็รู้

Security ดูตัวเลขเดียวก็รู้ว่าตอนนี้มีผู้มาติดต่อในพื้นที่กี่คน

06 — Edge cases

เมื่อเรื่องไม่เป็นไปตามแผน

กรณีสถานการณ์ระบบตอบสนอง

01การอบรมหมดอายุ

นัดใหม่ แต่ผลอบรมเดิมหมดอายุแล้ว

ระบบเช็คตอนสร้างนัด แจ้ง Visitor ทางอีเมล แล้วอบรมใหม่ที่หน้างานUX · รู้ก่อนเดินทางมา ไม่ถูกกันที่ประตู

02ยังไม่ยืนยัน Consent

มาถึงโดยยังไม่ยืนยัน Consent

ยังไม่ออก QR แต่ยืนยันที่หน้างานได้ก่อนเข้าพื้นที่UX · พลาดขั้นตอนก็ยังไปต่อได้

03เวลานัดไม่ตรงแผน

นัดเปลี่ยนหลังได้ QR หรือมาก่อนเวลา

QR เดิมยังใช้ได้ ระบบส่งอีเมลแจ้งเวลาใหม่ QR ใช้ได้ตั้งแต่ 15 นาทีก่อนนัดถึงสิ้นวันUX · ไม่ต้องรอ QR ใหม่

04สแกน QR ไม่ได้

แบตหมดหรือ QR Carbon หาย ทั้งที่ประตูและในพื้นที่

Security ค้นชื่อและตรวจบัตรประชาชน Host ค้นชื่อเพื่อยืนยันพบได้UX · QR เร็วที่สุด แต่ไม่ใช่ทางเดียว

05Walk-in ถูกปฏิเสธ

Host ปฏิเสธ Walk-in ที่ Security ลงทะเบียนไว้

เปลี่ยนเป็น ปฏิเสธ ไม่ออก QR Carbon และแจ้งเหตุผลบน Handheld ถ้าจะเข้าอีกต้องลงทะเบียนใหม่UX · ผลกลับมาที่ประตูทันที
07 — ผลลัพธ์

จากหน้าจอ สู่วิธีทำงานของโรงงาน

ระบบขึ้นใช้งานจริงแล้ว · ยังไม่มีตัวเลขวัดผล
Problem 01Host

เดิม · รับข้อมูลผู้มาติดต่อจากโทรศัพท์และอีเมล แล้วรวบรวมเอง

ตอนนี้ · ส่งลิงก์ให้ Visitor กรอกเอง ข้อมูลทุกทางรวมอยู่ที่เดียว

บริษัทได้ · ทุกรายการมีที่มาและตรวจย้อนได้

Problem 02Security

เดิม · ไม่รู้ว่า Host อนุมัติแล้วหรือยัง ต้องโทรถามเอง

ตอนนี้ · เห็นผลอนุมัติตอนสแกนที่ประตู ปกติไม่ต้องโทรถาม Host

บริษัทได้ · ออกแบบให้ลดการโทรประสานงาน และรู้ว่าใครเป็นคนอนุมัติ

Problem 03Security + Host

เดิม · ไม่รู้ว่าใครยังอยู่ในพื้นที่ หลังการเข้าพบจบแล้ว

ตอนนี้ · Host ยืนยันจบการพบ Security ยืนยันออกที่ประตู ปกติไม่ต้องไล่ถามกัน

บริษัทได้ · รู้ว่าใครยังอยู่ในโรงงาน

นอกจากนี้ ทุกรายการมีบันทึก Consent ก่อนออก QR

08 — บทเรียน

ระบบหลายบทบาท ต้องมีกฎก่อนมีหน้าจอ

01

สถานะต้องอิงสิ่งที่เกิดขึ้นจริง

ทุกสถานะบอกได้ว่า Visitor อยู่ขั้นไหน และใครเป็นคนยืนยัน
02

Flow บอกทาง แต่กฎบอกว่าไปต่อได้เมื่อไร

รู้ว่าใครทำอะไรได้ เมื่อไร และต้องผ่านเงื่อนไขอะไร ก่อนวาดจอ
03

กำหนดตัวชี้วัดตั้งแต่เริ่มโปรเจกต์

จับเวลาตั้งแต่ลงทะเบียนจนเข้าพื้นที่ไว้ก่อนใช้ระบบ เพื่อเทียบผลหลังใช้งาน
